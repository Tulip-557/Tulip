# skill 文档↔实现一致性审计

## 为什么需要

自建 skill 最容易出的错**不是代码写错，而是文档说的东西实际不存在**：
删了脚本忘改文档、改了字段名忘同步说明、写了「跑这个命令」但那个命令从没实现、
迁移了库却忘了装入口。

这类错**不会被任何测试抓到**——测试测的是代码，不是文档。它只在真正用起来时才暴露，
而且暴露方式往往很误导人。

> **实证（2026-09-27，verified-travel-planner）**：同一类错误在一天内连撞三次——
> ① 迁移了上游引擎却漏了配套 CLI，文档写着"跑确定性检查"但没那个命令；
> ② `data-contracts.md` 里 trip_request 的字段名（`date_start`/`group_type`…）
>    引擎完全不认，实际要的是 `start_date`/`budget_scope`…；
> ③ 删掉两个脚本后，SKILL.md 和 references 里仍有 3 处引用。
> 三次都是靠下面的核对查出来的。

## 怎么用

### 第一步：跑机械核对

```bash
python ~/.workbuddy/skills/skill-doc-code-audit/audit.py <skill目录>
python ~/.workbuddy/skills/skill-doc-code-audit/audit.py <skill目录> --runnable   # 顺带真跑 --help
```

查四件事：文档引用的路径是否存在 / 命令示例的脚本是否存在 / 占位标记（仅提示）。
退出码 1 表示有"文档说有、实际没有"的问题。

### 第二步：走人工清单（脚本查不了，但更值钱）

**① 字段名：从代码里 grep，不要抄文档**

```bash
# 找代码里真正定义必填字段的地方
grep -n "REQUIRED_FIELDS\|required_fields\|@dataclass" <skill>/engine/**/*.py
```

文档里出现的每个字段名，都要在代码里找得到。**反向也要查**：代码里的必填字段，
文档有没有写。

**② 错误码 / 状态枚举：正则抽出代码里的全部大写常量，与文档比对**

```bash
python -c "
import io,re
s=io.open(r'<文件>',encoding='utf-8').read()
print(sorted(set(re.findall(r'[\"\']([A-Z][A-Z0-9_]{4,})[\"\']', s))))
"
```

**③ 命令：真实跑一遍，正例 + 反例各一**

- 正例：正常的输入应当成功（退出码 0）
- 反例：构造一份**故意有问题**的输入，确认它真的被拦下（退出码非 0）

反例比正例重要——**只会通过的检查等于没有检查**。

**④ 迁移来的代码：核对"能力是否配了入口"**

从上游抄了库，不等于使用者能跑到它。逐项确认：

- 每个引擎模块有没有对应的命令行入口 / 调用路径？
- 入口的参数名、默认值是否与模块签名一致？
- 上游文档里承诺的错误码 / 退出码，本 skill 是否真的返回了？
  （上游常见做法是"打印报告就正常退出"，接进硬闸门时必须在非通过时返回非零）

**⑤ 覆盖度：上游的关键章节，本 skill 是否真的融合了**

用关键词 grep 抽查。例：怀疑漏了"随行套件"这一节，就 `grep -c "随行套件"`——
**0 处命中就是漏了**，别凭印象说"融合过了"。

**⑥ 完成标记：勾选框说的"做完了"，文件真的存在吗**

文档里的待办清单 / 完成标记（`[x]`、"已完成"、✅）**不是证据**。逐条把声称完成的东西
拿去文件系统对一遍——`ls` 有就是有，没有就是没有。**勾也是人勾的，同样会错。**

> **实证（2026-09-27，verified-travel-planner）**：README 的待办清单把 B 级 / C 级共 8 项
> 标成了 `[x]`，而对应文件（`browser-use.md`、`client-compatibility.md`、
> `validate_skill.py`、`tests/`、`.github/`、`.gitleaks.toml`、`examples/`）**一个都不存在**；
> 同一项目的开发日志里却明确写着"仍缺 B 级…C 级…"。两处矛盾，只能靠 `ls` 裁决。
> 纯读文档永远发现不了这个问题。

这条优先级很高：**误标的"已完成"比"漏写文档"危害大**——它会让人直接跳过一整块工作，
而漏写文档只是少个说明。

**⑦ 计数断言：文档里的「N 个 X」必须实测数一遍**

「引擎 15 模块」「26 项交付自查」「契约文档 18 章」这类**数字声称**，`audit.py` 一律验不了
（脚本自己就声明只查路径与命令存在性）。这类断言只能**现场数**：

```bash
ls -1 <skill>/engine/*/*.py | grep -v __init__ | wc -l        # 「N 模块」实际几个
```

```python
# 「N 项自查」实际实现了几个编号
import io
t = io.open('<文件>', encoding='utf-8').read()
nums = '①②③④⑤⑥⑦⑧⑨⑩⑪⑫⑬⑭⑮⑯⑰⑱⑲⑳㉑㉒㉓㉔㉕㉖'
have = [c for c in nums if c in t]
print('已实现 %d：%s' % (len(have), ''.join(have)))
print('缺失：%s' % ''.join(c for c in nums if c not in t))
```

> **实证（2026-09-27，verified-travel-planner）**：文档三处写「引擎 15 模块」，实测 **13** 个；
> 写「26 项交付自查」，代码里只出现 **18** 个编号（缺 `⑥⑩⑰⑳㉒㉓㉔㉕`），且 `--html` 模式
> **只跑其中一组**，实际覆盖率约 1/4。项目立身之本是「每个数字都有来源」，
> 结果自己文档的数字没人核。

数完必须**全文复查**：同一个数字往往散在多处（该案例里「15 模块」分布在 `AGENTS.md` 2 处 +
`README.md` 2 处，其中一处正是被 `| head -20` 截断才漏掉的）。改完用**无截断**的遍历再扫一遍确认归零。

**⑧ 状态描述也会过期——不只是"文件不存在"**

还有一类查不到：文档说的**状态**已经过时。README 里写「`experience.md` 的记录区仍是空的」
「项目至今零实战」，而该文件早已填好、实战早已跑过。这类句子读起来完全确定，
**判断它必须回到文件本身**，不看它语气多肯定。

**⑨ 自查脚本的「全绿」：它到底查了几项？**

看到脚本输出「✅ 全部通过」先别松口气——**要问它那份检查清单覆盖了几项**。
一个只跑了 4 项却说"全部通过"的脚本，比不跑更容易骗人：**那个绿是「只剩这几项可查」的绿。**

查法：

1. 列出脚本里**真正产生判定**的检查项。⚠️ **出现编号 ≠ 做了检查**——有的编号只写了
   `stat['x'] = n` 的统计，从未进入 `bad` 列表，等于没查。
2. 与文档声称的项数比对，算出**真实覆盖率**。
3. 覆盖率 < 100% 时，要求脚本**自己输出覆盖声明**（「本次实检 N/M，未覆盖：…」），
   而不是指望使用者记得。

> **实证（2026-09-27，verified-travel-planner）**：`ludbook_check.py` 号称「26 项机械核对」，
> 但 `--html`（HTML 交付路径）实际只跑 C 组 4 项——A 组证据溯源、B 组内容完整**完全不跑**，
> 真实覆盖率约 1/4；其中编号 ⑦ 更只是 `re.findall` 存了个计数、从未参与判定。
> 修复后覆盖 19/26，并在结尾打印「本次实检 19/26（阻断 17 ｜ 提示 2）」+ 未覆盖 7 项。
> 同一改动下，一份被旧脚本判"全绿"的示例立刻露出 2 项真缺口——**证明旧的那个绿是残缺的**。

**⑩ 检查项的判据必须与文档口径对齐，否则噪声会淹掉闸门**

写或改检查项时，先回读**该检查项的文档原文**再划判据。判据过宽 → 大量误报 →
**闸门被使用者绕过，比不设闸门更糟**。

> **实证（2026-09-27）**：某「数字溯源」检查最初写成「任何 `¥金额` 都要有来源」+「表格里的
> 数值逐行判」，一份 3 天路书被报出 **55 处**"裸数字"——其中 14 行是表格内共享表外一处来源的
> 里程，其余是预算汇总、复述行、茶点单价。回读原文后收窄为「票价仅指门票/车票一类决策依赖
> 价格」+「整表可回溯来源则整表撤出，并把表内数值登记进已溯源池」，同一份路书 **55 → 0**。

**降噪不能降成哑巴**：放宽判据后必须另造一份**完全没做该工作**的样本，确认它仍然报错。

**⑪ 代码里引用的本包文件，是否真的存在**

`audit.py` 只扫**文档**里的路径，**代码字符串**里引用的本包文件它看不见。
2026-09-27 实测踩到：`diagnostics.py` 的报错文案让用户去「运行 `setup_rail_mcp.sh`」，
而该脚本在上游有、本仓库**根本没搬过来**——`doctor` 于是给出一条**走不通的指引**，
`audit.py` 却报「✅ 未发现问题」。

```bash
# 代码里出现的本包文件名（.sh / .patch 最可疑，.md 次之）
grep -rnoE "[A-Za-z0-9_.-]+\.(sh|patch)" <skill>/engine <skill>/tools | sort -u
```

逐个确认：是**本包文件**（须存在）还是**外部项目的文件名**（如 `pyproject.toml`，忽略即可）。
误报提示：`hashlib.md5` 这类属性访问会被正则截成 `hashlib.md`，忽略；`Binary file ... matches`
是 `__pycache__` 命中，先清缓存再扫。
**指引型文案比路径引用更容易漂移**——它不在 import 链上，改文件名时没人会想起来同步它。

## 输出

给一份发现清单，每项写清：**文档在哪说的 → 实际是什么 → 改文档还是补实现**。
不要笼统说"文档有点旧"，要能直接照着重现。

## 注意

- 模板类文档（如 `<skill>/assets/*模板*`）**本来就该带 TODO**，占位标记是设计意图，
  只提示不当错误。但要确认**报错方式不误导人**——把"模板占位没替换"报成
  "文件不存在"会让人查错方向。
- 审计自身也要能跑：先对 audit.py 用一份健康的 skill 跑一遍，确认输出合理。
- **改完必须重跑**。这类问题的特点是"改一处漏一处"，一次修完不复核等于没修。
- **扫描别加 `| head -N` 截断。** 截断后的输出**看起来就像完整结果**，极易被当成全量事实——
  2026-09-27 就因此漏掉一处「15 模块」（输出恰好被切在第 20 行），第二轮无截断全量遍历才抓到。
  **「输出停下来了」不等于「结果就这些」。** 确实需要限量时，让脚本自己统计并打印总数
  （如 `命中 N 条`），而不是靠 shell 截断。
- **跨 Bash / Windows Python 传文件，一律用真实 Windows 路径**（如
  `C:\Users\<用户名>\AppData\Local\Temp\`）。Git Bash 的 `/tmp` 与原生 Python 的 `/tmp` **不同源**：
  Bash 里 `cmd -o /tmp/x.json` 确实写出了文件，但 Python 打开 `/tmp/x.json` 会 `FileNotFoundError`。
